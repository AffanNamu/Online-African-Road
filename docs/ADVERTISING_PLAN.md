# In-game roadside advertising and billboard management: inspection and technical implementation plan

Written 2026-11-08 in answer to the owner's brief "ARO: in-game roadside advertising and billboard management system". **This is the inspection and the plan the brief asks for first. Nothing is built, no migration is written, no Supabase or admin change is made.** The feature touches the database, the admin site, authentication, media storage and (later) money, so every item marked **APPROVAL** below needs the owner's decision before work on it starts (`CLAUDE.md`: no Supabase or production-configuration change without separate approval).

## 0. The answer in one page

| Question | Answer |
|---|---|
| Can the existing Admin Dashboard be extended, or is a separate one needed? | **Extend it.** It is a static site (no framework) that calls database functions; roles, two-step sign-in (TOTP), an append-only audit log, required reasons, rate limits and a strict content-security policy already exist, and its News and banners feature (draft, scheduled, live, expired; server-cleaned text; preview) is the pattern a campaign needs. A second dashboard would duplicate all of that. |
| Is a separate advertising backend needed? | **No.** Same Supabase project, same authentication and the same rule that every write is a `SECURITY DEFINER` function that checks the caller's role. New tables and functions, added by new forward-only migrations. |
| Does the game already deliver remotely managed content? | **Yes, for text.** `get_content('news'\|'hero')` returns the items that are live now (server clock); the dashboard shows them. It has **no media** (no images are downloaded) and **no cache or fallback layer of its own**. Advertising adds image delivery, which does not exist yet. |
| Does media storage exist? | **No.** Nothing uses Supabase Storage today (no bucket, no storage policy). Media storage is a new capability: **APPROVAL** (section 5). |
| Do billboards exist in the game? | **One placeholder prop** (`billboard`, 8 x 8 m, flat colour panel, placed every 400 to 600 m in industrial and highway zones plus one hand-placed set piece). It cannot show an advertisement. 3D billboard assets must be modelled (Blender), registered in ARO-CONTENT and integrated; section 6. |
| Biggest risks | (1) images on large boards cost texture memory and draw calls, and the world is batched per chunk: solved by one shared atlas for all ad faces (+1 draw call), not a texture per board; (2) impression numbers that over-claim: solved by separating **measured exposure** from **estimated reach** at the data level; (3) abuse by anonymous advertisers: solved by never publishing from an external submission and never serving advertiser files to players; (4) payments: **not built**, only prices as data. |
| What I need from you | The decisions in section 11 (storage, enquiry hosting and anti-abuse, the new `advertising` admin role, content rules, privacy wording, and whether to proceed with phase A). |

## 2. Gaps (what the brief needs that does not exist)
No advertising data model; no media storage; no image delivery or cache in the game; no impression or interaction measurement; no enquiry intake from outside; no placement inventory; no billboard 3D assets that can show a changing image; no price, package or currency data; no campaign states, conflict rules or approval workflow; no admin pages for any of it.

## 3. Architecture (the seven parts of the brief, mapped to what is reused)

| Part | Design | Reuses |
|---|---|---|
| 1. Inventory and placement | `ad_boards` (one row per physical board in the world: stable id, route, city, district, road label, station along the route, side, type, size, faces, illuminated, status) and `ad_slots` (the faces of a board). **Board ids come from the game's own data**: a board is an instance of a billboard prop in the route data, and its id is `routeId:ruleId:slot` (scatter) or the placement id (hand placed), deterministic and tested. A generator (`tools/gen_ad_inventory.py`, like `gen_game_seed.py`) writes idempotent seed rows from the route data; CI checks the seed is current. The admin chooses assignments; it never invents boards. | route data, seed generators, `PropScatter` determinism |
| 2. Advertiser enquiries | `ad_enquiries` (business, contact, category, description, preferred locations and duration, message, artwork, state new / contacted / approved / rejected / converted, notes) behind `submit_ad_enquiry` (anonymous callers allowed, strictly validated and rate limited) and admin functions to list, annotate, approve, reject and **convert to a campaign**. An enquiry **never** creates a published advertisement by itself. | rate-limit buckets, admin function pattern |
| 3. Campaigns | `ad_campaigns` (advertiser, title, creative reference, package, dates, state: draft, in_review, approved, rejected, scheduled, live, paused, ended, terminated) and `ad_assignments` (campaign x slot x period). The state shown is **computed from the server clock** like news states (a campaign is live only inside its dates and while active). A database constraint (exclusion on slot and period) makes two live assignments on one slot at the same time impossible. | news and banner schedule logic |
| 4. Media and artwork | creatives are **images only**, validated and **re-encoded** (metadata stripped) to fixed sizes and formats; advertiser uploads are quarantined and never served to players; players only ever receive the processed, approved copy. Storage choice in section 5 (**APPROVAL**). | none today |
| 5. Game-side delivery | one read function `get_ad_manifest(route, since_version)` returns the active creative per slot (slot id, creative id, content hash, url, size, kind static or rotating) with a manifest version; the game fetches it at most every few minutes, downloads **only images for boards near the player**, keeps them in a bounded memory cache (and the browser's HTTP cache), and shows **fallback artwork** whenever anything is missing. Section 7. | `get_content` pattern, `SupabaseClient` retry |
| 6. Analytics | measured exposure (client-measured, server-validated, aggregated, PII-free) kept apart from estimated reach (computed from traffic); section 8. | `analytics_events` pattern (new allow-listed names or a separate aggregate table) |
| 7. Admin controls | a new **Advertising** area in the existing admin site (inventory, campaigns, enquiries, packages, reports) calling `admin_ad_*` functions with the same checks, reasons and audit trail. | whole admin stack |

**New tables (draft names; migrations are forward-only and additive):** `ad_packages`, `ad_boards`, `ad_slots`, `ad_advertisers`, `ad_enquiries`, `ad_creatives`, `ad_campaigns`, `ad_assignments`, `ad_exposure_daily` (aggregates), `ad_clicks_daily`. No table is client-writable; reads go through functions listed in `api_surface.txt`.
**New roles:** `advertising` (campaigns, creatives, enquiries, boards) in addition to `owner` (everything, including pricing and termination); `analyst` may read reports; `content`, `support`, `operations` have no access. Adding a role re-creates `admin_set_role` exactly as the `content` role did (**APPROVAL**).
**Audit events (append-only, with reason):** campaign created, edited, submitted, approved, rejected, scheduled, activated, paused, resumed, ended, terminated; assignment added or removed; creative uploaded, approved, replaced, removed; enquiry state changes and conversion; package created, price or currency changed, inventory changed; board status changed; every report export.
**Server-side checks (every function):** signed in, active admin, `aal2`, role allowed for that function, reason where something changes, input validation, rate limit. Players and anonymous callers get `not_admin`, except the three public functions: `submit_ad_enquiry` (anonymous, rate limited), `get_ad_manifest` and `record_ad_exposure` (player).

## 4. Roles of money: packages, prices, currencies (no payments)
`ad_packages`: code, name, board type, size class, duration options (days), **price in minor units plus ISO 4217 currency code** (NGN first; any other currency is just another row), available inventory (count or specific boards), active flag. Nothing is hard-coded; changes are audited. A package can have prices in several currencies. Campaigns store the price **as agreed** (so later price changes do not rewrite history). **No payment provider, no checkout, no charging, no invoices are built**: payment status on a campaign is a manual field (`unbilled`, `invoiced`, `paid`, `waived`) set by an owner with a reason, and the provider interface is a documented extension point only until the owner reviews a payment workflow (**APPROVAL, deferred by design**).

## 5. Media and artwork storage (**APPROVAL**)
Options for the owner:
* **A (recommended): Supabase Storage with two buckets.** `ad-quarantine` (private; admins only; size and MIME limited) and `ad-public` (public read; processed images only; immutable names containing the content hash, so they can be cached for a long time). The admin page re-encodes every image in the browser (canvas, strips metadata, fixed dimensions) before upload, and the database function that attaches a creative checks that the object exists in the right bucket, its size and its type. Needs Storage switched on and storage policies (a configuration change in the project).
* **B: images in the database** (`bytea`, at most 150 KB each, served through a function as base64). No new service, but heavier responses and no CDN caching; acceptable for a pilot of a few dozen creatives, not for scale.
For **external advertisers' artwork** (an anonymous submission): option B-style only, in a private table with a hard size cap (300 KB), magic-byte checks and never served to players; an admin views it in the admin page (rendered through a canvas, so a hostile file is never interpreted), then re-encodes and approves a processed copy. No anonymous upload ever reaches a bucket. Virus or content scanning is not available in this stack: the re-encode removes everything but pixels, and a human approves every creative.
Creative sizes (draft): static boards 1024 x 512 (2:1), 1024 x 341 (3:1 wide), 512 x 1024 (portrait), LED 512 x 288 (16:9) with up to 6 rotating frames; JPEG or WebP, at most 150 KB each; a neutral fallback image per aspect ratio ships in the game build.
**Link validation:** `https` only, no credentials in the URL, no redirects followed by the game, host not an IP address, a block list the owner can extend; the game never loads a web page itself: a link opens only after an explicit player action (section 8).

Every asset: one separate **`AdFace`** mesh per face (UV 0 to 1 over the whole face, flat, a distinct material slot `M_AdFace`), recorded in its manifest as an **ad slot** with real width, height and aspect; frame, poles, catwalks and lamps in other slots; LODs (the face stays one quad at every LOD; the frame drops detail); collision (box or capsule on poles only, none on the face); triangle budget per LOD; dimensions in real metres; registry entry with id, class, intended use, Blender source, export, validation, Unity prefab reference. The chain stays reference -> Blender -> export -> Unity prefab -> placement -> in-game review, and nothing is marked approved without the owner's visual review.
**Placement rules (tested, data-driven):** only inside a zone and profile the rule names; a minimum spacing between boards (at least 250 m on the same side of the same road); never within 60 m before a road sign, gantry or junction mast and never in front of one (a sign-clearance test over the real route); set back from the carriageway edge by a minimum that depends on the type; oriented to face oncoming traffic with a legible viewing distance (face height x 100 as the design reading distance); never on the median of a divided road; none on bridge decks unless a bridge-board type is declared; a density cap per kilometre by zone (for example at most 2 per km on highways, 4 per km in commercial streets) so the game does not become visually noisy; the owner can switch a rule off in route data. Night: boards marked illuminated get lamp heads and a face that brightens with the lamp factor; LED boards are self-lit.

## 7. Game-side delivery, cache, failure and performance (the game must never depend on it)
1. **Boot:** the game starts and plays with the bundled fallback artwork. Advertising never blocks sign-in, loading, the menu or driving.
2. **Manifest:** `get_ad_manifest` is requested lazily (after the world is up, then every 5 to 10 minutes, with the last manifest version so an unchanged manifest costs a few bytes). Any error (network, 4xx, 5xx, bad JSON, expired token) is logged once and ignored; the last good manifest stays in use; a manifest older than 24 hours is dropped and the fallback returns.
3. **Images:** only for boards within a streaming radius (about 400 m) and only when the board is not already showing the right creative (matched by content hash). One download at a time, small files, a hard timeout, a memory cache with a byte cap (about 8 MB), least recently used eviction, the browser's HTTP cache for the rest. A failed image is retried with back-off and never repeated in a loop; a board whose image never arrives keeps the fallback.
4. **Display:** all ad faces of loaded chunks share **one atlas material** (a fixed grid of slots, for example 2048 x 1024 with 512 x 256 cells, uploaded cell by cell as images arrive): **+1 draw call for all boards**, no texture per board, no change to the chunk batching, memory capped (about 8 MB). A board's UVs point at its cell; a missing creative points at the fallback cell. LED boards cycle several cells on a timer (a UV change, no new texture).
5. **Night:** the face brightness follows the existing lamp factor for illuminated boards (a multiplier on the atlas material per board class), LED boards stay lit.
6. **Isolation:** the ad system runs on the main thread in small steps under a frame budget, touches no physics, no navigation, no multiplayer state; the faces have no colliders; a test proves the system compiles out when the manifest URL is absent.
7. **Performance budget (to be measured, not assumed):** +1 draw call, at most 8 MB of texture memory, no per-frame allocation, no download while the vehicle is above a speed threshold if the connection is slow (optional), `[Ads]` log lines (boards visible, cells used, bytes, failures) and a CI check next to the draw-call and texture budgets.

## 8. Analytics: measured against estimated (never mixed)
* **Measured exposure** (what the client observed): a board counts as **exposed** only while it is within its design reading distance, inside the camera's view, facing the player within an angle limit, **not occluded** (a cheap ray check from the camera) and showing a real creative (not the fallback). The client accumulates seconds per board and sends batches (`record_ad_exposure`) rate limited per player; the server caps and validates (a plausible maximum per minute, per session, per board), stores **aggregates only** per day, slot, campaign and player-count bucket (no player id kept with the exposure row, no personal data). A **view** (counted impression) is defined as at least 1.5 seconds of exposure in one pass; the definition is shown next to every number.
* **Estimated reach** (a model, labelled as an estimate): passes of players along that stretch of the route (from sessions and telemetry the game already records) multiplied by the share of passes that had the board in the reading distance; **never presented as people who saw the advertisement**.
* **Loaded is not viewed:** a creative loaded into the atlas, or a board streamed in, is not an impression. The reports show three separate columns: loaded (diagnostic), measured exposures, estimated reach.
* **Interactions:** where supported, a stopped vehicle near a board can show a small prompt (for example "Learn more"), and an explicit key press opens the https link in a new tab after a confirmation; clicks are counted as aggregates. Not available on every platform; the report says "not supported" rather than zero.
* **Reports:** per campaign and per location: total measured exposures, estimated reach, campaign duration, active placements, advertiser, status, clicks; export as CSV (audited). Privacy: no personal data, no cross-session tracking; wording for the player-facing privacy notice is a decision for the owner (**APPROVAL**, and a legal review for the markets involved).

## 9. Advertiser enquiry workflow
Public form (a small static page, separate from the admin site and from the game) -> `submit_ad_enquiry` (validated: lengths, e-mail format, phone, category from a list, preferred locations from the inventory, duration from the packages, artwork at most 300 KB image, honeypot field, per-contact and global daily caps, no HTML kept) -> admin **Enquiries** list (new, contacted, approved, rejected, converted; notes with audit) -> **Convert to campaign** (copies the facts into a draft campaign, never publishes) -> review -> approve -> schedule. Contacting the advertiser is done by the team outside the system (e-mail, phone, WhatsApp links are shown, nothing is sent automatically). A CAPTCHA would need a third-party service: not assumed (**APPROVAL**).
