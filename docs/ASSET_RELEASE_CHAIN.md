# The release chain of an asset (owner requirement, 2026-11-07)

For every asset release of the reusable African environment library (not only Kano) the chain must be preserved and checkable:

**reference** (the concept, a registered reference id) -> **Blender source** (`.blend` in the private repository, Git LFS) -> **exported files** (FBX, GLB, package manifest, original export manifest) -> **Unity prefab** (generated by the importer; recorded by the Unity import report, never committed) -> **validation** (the Blender validation report, passed) -> **in-game review** (pictures from the running game, then the owner's decision).

`tools/release_chain.py` checks it against a checkout of an `assets/...` branch of the private repository `AffanNamu/ARO-CONTENT`:
```
python3 tools/release_chain.py --content <checkout> --reviews <checkout>/previews/in_game_review/<date> [--json chain.json]
```
Each link is **ok**, **open** (not reached yet: legitimate, e.g. the owner has not reviewed) or **missing/mismatch** (broken: exit code 1). Rules it enforces: every concept id must exist in `docs/kano/reference_register.json`; an asset with no concept must record why (a documented reference gap `M-nn` or an owner request) and stays open; the export needs FBX, GLB and manifest; the Unity import report must list the asset with LOD triangles and material count equal to the registry's; the validation report must have `passed: true`; **the in-game review link is only ok when the registry records the owner's visual review**: pictures alone leave it open. It never writes a registry and never marks anything approved.

**Where each link lives for a release:** registry entry `registry/asset_registry.json` (`concepts`, `blenderSource`, `export`, `validation.blender`, `validation.unityImport`, `validation.visualReview`, `library`, `status`); frozen hash manifest `docs/kano/*.freeze.json` of the game repository; fresh-clone verification `tools/verify_asset_clone.py`; review pictures `previews/in_game_review/<date>/` (`runs.json` names the run, its commit and the artifact).

**Result on 2026-11-07** (branches pushed and verified the same day): `assets/kano-residential-v2` 14 assets, 84 links: 55 ok, 29 open, 0 broken; `assets/kano-residential-v3` 14 assets: 69 ok, 15 open, 0 broken; `assets/environment-kit-v1` 26 assets, 156 links: 127 ok, 29 open, 0 broken. Open: the in-game review of every asset (the pictures are preserved, the owner has not decided), the Unity import of the v002 package (v002 was imported in run 41391901470 but its registry entry on that branch predates the import record), and the reference of the pole (owner request) and the three Hausa assets (gap M-01). **No asset has a complete chain yet, because no asset has been through the owner's in-game review.**

## For new releases
1. Register the reference first (`docs/kano/reference_register.json` of the planning package) or record the gap.
2. Build, validate, export, freeze (hash manifest), stage into the private repository, push as LFS, verify through a fresh clone.
3. Import into Unity through the review job and keep its import report.
4. Run the review, preserve the pictures (`previews/in_game_review/<date>/`), then ask the owner. Only the owner's decision sets `visualReview` and, later, `production_approved`.
