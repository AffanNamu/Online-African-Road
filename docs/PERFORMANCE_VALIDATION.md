# Validating the cost of post-processing (Neutral tonemapping) on real hardware

**Status: not validated on any real GPU.** Everything measured so far is from CI, which renders the WebGL build in headless Chromium with a **software** (CPU-emulated, SwiftShader) driver.
That measures how much *work* a change adds; it does not predict how long a real mobile or desktop GPU takes, and it must not be quoted as device performance.

## What happened and what was measured (software renderer only)
Until commit 0634c3c the renderer asset generated by `SceneBuilder.EnsureUrp` had no post-process data, so the Volume built by `RenderingRig` (tonemapping on every tier, colour grade and vignette on Medium and above) was never drawn.
Fixing that makes every tier draw an HDR-to-display full-screen pass. In the CI browser test the Low tier's average frame time went from about 142 ms to about 176 ms (+24%, six `[Perf]` samples each, commit 550f9fd against 28ba0ee),
and a camera test whose 5-second wall-clock window measured 41 m began to measure 26 m. The Low tier's design (`QualityTiers.Low`) always listed `Tonemapping = true`; that setting had simply never been exercised.

**Decision (project owner):** keep the **Neutral** tonemapper on as the default, including at Low, while the real cost is investigated. `?tonemap=none` removes it (and `?tonemap=aces` restores ACES) for A/B comparison; no code change is needed to measure.

## What CI records now
Each lighting pass prints `software-GL frame time ... (NOT a GPU measurement)` per hour, and CI renders the Low tier with Neutral (default), ACES and no tonemapper, so the *software* cost of each is on record in every run
(`webgl-light-metrics.json`, `webgl-light-none-metrics.json`, `webgl-light-aces-metrics.json`, field `softwareFrameMs`).

## Plan to validate on hardware
Devices (at least one of each; record model, OS, browser and version):
1. A low-end Android phone (the Low tier's target) in Chrome.
2. A mid-range Android phone in Chrome.
3. An iPhone in Safari.
4. A laptop with an integrated GPU (Chrome and Firefox).
5. A desktop with a discrete GPU (Chrome).

Procedure for each device, 3 repetitions each, device plugged in or at a stable charge, no other heavy apps, let it cool between runs:
1. Open `<build>/index.html?smoke=drive&hold=1&hour=noon&quality=low` (the truck is frozen in place, so the scene is identical every time). Wait 20 s, then record 60 s of the game's own `[Perf] avgFrameMs=` lines.
2. Repeat with `&tonemap=none` appended (A/B). Then repeat both at `quality=medium`.
3. Where the browser supports `EXT_disjoint_timer_query_webgl2`, also record GPU time per frame; otherwise use the browser's performance profiler (Chrome DevTools Performance panel, Safari Web Inspector timelines).
4. Record median and 95th percentile frame time, plus any thermal throttling seen (frame time rising over the 60 s).

Decision rule: the Low tier budget is `PerfBudget.Mobile` (33.3 ms per frame). If, on the low-end reference phone, the default tonemap pushes the median above that budget or adds more than about 1.5 ms (or 5%) over `tonemap=none`,
bring the numbers back and decide between: tonemapping off for the Low tier only (the tier flag already exists), a cheaper tonemap setting, or a lower Low-tier render scale. Until then the Neutral default stays and the cost is **unvalidated**.
